# 检索问答阶段设计方案（Web QA 服务）

> 对应《数据处理阶段设计方案.md》之后的在线问答阶段。数据管线（step0~step5）产出的
> Milvus 向量库与本设计方案衔接，形成完整可用的财报 RAG 问答系统。
> 本文档为设计稿，不含实现代码；所有需要 LLM 参与的步骤均给出完整提示词（§9）。

---

## 1. 需求回顾与总体流程

| # | 需求 | 设计落点 |
|---|---|---|
| 1 | 意图识别：与财报无关则委婉拒绝 | §4 S2（提示词 P1） |
| 2 | 查询改写：更详细结构化输出；多意图拆成多条查询；每条带缩小检索范围线索（公司 + 报告期 + 报告类型） | §5 S3（提示词 P3） |
| 3 | 检索：多意图多路召回，BM25 + 向量混合 | §6 S4 |
| 4 | 召回充分性判断：不足则回到检索补充，最多循环 3 次 | §7 S5/S6（提示词 P4） |
| 5 | 基于召回内容回答；信息不足直接告知用户 | §8 S7（提示词 P5） |
| 6 | 会话记忆：容量到限压缩；关闭 Web 即清空 | §3 S1（提示词 P2） |
| 7 | Web 形式提问 | §2 |

### 1.1 请求生命周期总览

```
用户在 Web 页面提问
        │
        ▼
[S1 会话记忆模块] ── 容量超限 ──> [P2 记忆压缩]（滚动压缩）
        │ 提供对话历史
        ▼
[S2 意图识别（P1）] ── 财报无关 ──> 委婉拒绝话术，直接返回（不走检索）
        │ 财报相关
        ▼
[S3 查询改写（P3）]  产出 N 条子查询，每条带 filters（公司/报告期/报告类型）
        │
        ▼
[S4 混合检索]  每条子查询独立执行：向量检索（Milvus）+ BM25 检索 -> RRF 融合
        │
        ▼
[S5 证据归并与重排序]  候选按 文件+页码 去重 -> 回查整页原文 -> qwen3-rerank
        │              打分 -> 本轮取 top5 页，与历史轮次证据池去重追加
        ▼
[S6 充分性判断（P4）] ── 不充分且轮次<3 ──> 生成补充查询（带 filters）──> 回到 S4
        │ 充分 或 已循环 3 次
        ▼
[S7 回答生成（P5）] ── 全部子问题无依据 ──> 信息不足话术，直接告知用户
        │
        ▼
回答（含来源标注）返回 Web；本轮问答写入 S1 记忆
```

> 说明：S6 不充分但已到第 3 轮时，仍进入 S7 降级处理——能答的部分作答并注明缺口，
> 完全无依据则直接告知信息不足（不编造）。

## 2. Web 服务与会话管理

### 2.1 技术选型

- 服务端：FastAPI（与现有 Python 技术栈一致），单进程即可（单用户/低并发场景）。
- 前端：单页 HTML（`webapp/index.html`），无框架依赖，fetch 调用后端接口。
- 服务纯内存保存会话，**不落盘**——"关闭 Web 即清空记忆"由生命周期机制天然保证。

### 2.2 会话生命周期（记忆清空机制）

| 事件 | 行为 |
|---|---|
| 首次访问 / 点击"新对话" | 创建 `session_id`，分配全新记忆空间 |
| 页面关闭 | 前端 `unload` 时 `navigator.sendBeacon("/api/session/close")` 通知服务端销毁会话 |
| 连接异常中断 | 服务端 SSE/WebSocket 断开事件兜底销毁会话 |
| 空闲超时（默认 30 分钟，可配置） | 定时器扫描，超时会话直接销毁 |
| 服务重启 | 全部会话自然丢失（内存态，可接受） |

### 2.3 接口定义（设计层面）

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| GET | `/` | — | 问答页面 |
| POST | `/api/chat` | `session_id, message` | `reply, sources[], insufficient, elapsed_ms` |
| POST | `/api/session/new` | — | `session_id` |
| POST | `/api/session/close` | `session_id` | 销毁会话 |

`reply` 内含来源标注文本；`sources[]` 为结构化来源（`report_name/company/report_type/period/page`），供前端渲染引用列表。证据粒度为**整页**（不再是 chunk）。

## 3. S1 会话记忆管理模块

### 3.1 数据结构（内存态）

```
SessionMemory:
  session_id: str              # uuid4；/api/session/new 时生成，/api/chat 按它定位会话；
                               # 内存态不落盘，随会话销毁而清空
  created_at: datetime         # 会话创建时间
  last_active_at: datetime     # 最后活跃时间（每次 /api/chat 刷新；§2.2 空闲超时扫描依据）
  summary: str                 # 压缩摘要（初始为空）
  messages: [                  # 原文消息，仅保留最近若干轮
    {
      message_id: str,         # uuid4；每条消息的唯一键（日志排查、前端渲染 key）
      turn_no: int,            # 轮次号，从 1 递增；同一轮问答的 user/assistant 共享
      role: user|assistant,
      content: str,
      tokens: int
    }
  ]
  total_tokens: int            # tokens(summary) + sum(messages.tokens)
```

三级键的分工：

| 键 | 级别 | 用途 |
|---|---|---|
| `session_id` | 会话 | 定位会话；串联该会话的全部日志 |
| `turn_no` | 轮次（每次问答交互） | "每次对话"的唯一键；压缩按轮取最旧、`keep_recent_turns` 按轮保留 |
| `message_id` | 消息 | 单条消息定位与幂等参考 |

### 3.2 容量与压缩策略

- 计量口径：tiktoken `o200k_base`（与现有 chunking 配置一致）。
- 阈值（可配置，默认值）：`max_memory_tokens = 3000`，`keep_recent_turns = 4`。
- 触发：`total_tokens > max_memory_tokens` 时压缩。
- 压缩动作：
  1. 取 `messages` 中最旧的若干轮（保证剩余最近 4 轮原文）；
  2. 调用 P2 将其与现有 `summary` 合并压缩为**新摘要**（滚动压缩，摘要本身超限时对摘要再压缩）；
  3. 用新摘要替换旧摘要，被压缩的消息从 `messages` 移除。
- 记忆进入 S2/S3 的形态：`summary + 最近 4 轮原文`。

### 3.3 为什么摘要必须保留实体线索

压缩摘要的最高优先级是**保留 公司名/股票代码、报告期、报告类型、已确认的事实要点**——
它们是查询改写（S3）继承过滤线索的来源。摘要丢失实体 = 下一轮改写无法确定公司，
检索范围会退化到全库，所以 P2 中将实体列为"必须保留"项。

## 4. S2 意图识别（LLM，提示词 P1）

- 输入：当前问题 + 会话记忆（summary + 最近轮次）。
- 输出 JSON：`{is_financial_qa, reason, confidence}`。
- **无关 → 委婉拒绝**：使用固定话术模板（可配置），不走后续任何步骤。固定模板而非 LLM
  生成的原因：拒绝话术要求稳定、可控、无幻觉。
  默认模板：
  > 抱歉，我是财报问答助手，目前只能回答与上市公司财报相关的问题（如经营业绩、财务指标、
  > 报告章节内容等）。您可以换个财报相关的问题，我很乐意帮您查询～
- **相关 → 继续 S3**。
- **拒绝轮写入会话记忆**：拒绝时同样把本轮 user 提问 + assistant 拒绝话术写入 S1
  （正常计 token），保证用户后续追问（如"刚那个问题呢"）的上下文连贯。
- 边界决策：`confidence < 0.5` 时**按相关放行**（宁可多检索、不误拒绝；误拒的体验代价
  高于一次无效检索）。
- 失败处理：JSON 解析失败重试（复用 `llm.max_retries`）；仍失败则向用户返回"服务暂时
  不可用"并记录日志——不做静默兜底。

## 5. S3 查询改写（LLM，提示词 P3）

### 5.1 与 CASEA-Query改写 的关系

沿用其五类型划分（上下文依赖 / 对比 / 模糊指代 / 多意图 / 反问）作为改写规则来源，
但**不做"先分类再路由"的两段式**，改为**单次调用直接输出结构化查询计划**——分类与改写
合并，减少一次 LLM 调用，且多意图拆分天然融入输出结构。

### 5.2 缩小检索范围线索（filters）

语料库元数据（来自 file_manifest，逐块入库）决定了可用的过滤维度。在此之上确定四项线索：

| 线索 | 字段 | 说明 |
|---|---|---|
| 公司（需求给定的基线） | `company` + `stock_code` | 最强过滤项；确定公司可把检索范围缩到该司全部报告 |
| **线索一（新总结）** | `period` 报告期 | 年份/半年（如 `2024`、`2024H1`）；财报问答绝大多数问题有明确期间指向，是仅次于公司的强过滤项 |
| **线索二（新总结）** | `report_type` 报告类型 | 年报/半年报/一季报/三季报；同一公司同年有多份报告时用于精确到单份 |
| （可选扩展，本期不做） | `section_topic` 章节主题 | 管理层讨论/财务报表/风险因素等；需要步骤3摊平时增加章节标注，列为后续迭代项 |

> 选报告期与报告类型的理由：两者都是语料库现成元数据，可直接映射为 Milvus 标量过滤和
> BM25 分域过滤，零额外加工成本；且二者组合（公司+期间+类型）通常能定位到**单份报告**。

### 5.3 结构化输出设计

单次调用输出完整查询计划，`sub_queries` 统一为数组（单意图即单元素），下游无须分支处理；
`query_type` 取单词枚举：`single`=单意图、`multi`=多意图、`compare`=对比、`rhetorical`=反问还原：

```json
{
  "query_type": "single | multi | compare | rhetorical",
  "sub_queries": [
    {
      "id": 1,
      "rewritten_query": "自包含的完整检索语句，公司+期间+主题写全",
      "search_intent": "这条子查询要查什么（一句话）",
      "filters": {
        "company": "中芯国际",
        "stock_code": "688981",
        "period": "2024",
        "report_type": "年报"
      },
      "keywords": ["营业收入", "同比增长"],
      "confidence": 0.9
    }
  ]
}
```

关键规则（全部写入 P3）：

1. **指代消解**："它/这个/都/还有"等从对话历史解析，优先继承上一轮的公司、期间、类型。
2. **多意图必拆**：多个可独立回答的子问题 → 多条子查询；**对比型按对比对象各生成一条**
   （如"A 和 B 哪个更 X"→ 查 A 的一条 + 查 B 的一条），对比综合留给 S7 汇总。
3. **反问还原**：先转中立客观的信息需求，再进入拆分。
4. **禁止猜测**：filters 只允许取自"用户明确说出"或"对话历史已确认"的信息，
   无法确认一律 `null`（检索时该维度不加过滤）——严禁编造公司名/年份/报告类型。
5. **语料库范围注入**：调用时把 file_manifest 中已入库的 `公司清单、年份清单、报告类型枚举`
   作为参考信息传给模型，降低编造概率、便于对齐枚举值（如"年报"而非"年度报告"）。
6. `rewritten_query` 必须自包含（即使 filters 已有公司名，查询句中也写全公司+期间+主题），
   保证 BM25 与向量检索不依赖 filters 也能工作。
7. `keywords` 为该子查询的核心词项（指标名/主体名，2~5 个，不含 filters 已含的公司/
   期间/类型值），供 S4 BM25 查询扩展使用——产出即消费，不是死字段。

### 5.4 与 S4/S6 的对接

- `sub_queries[]` 逐条进入 S4 独立召回（多意图 = 多路召回）。
- S6 生成的补充查询复用同一 `{query, filters}` 结构，进入同一检索通道。

## 6. S4 混合检索（非 LLM）

### 6.1 双路召回

| 路 | 引擎 | 要点 |
|---|---|---|
| 向量 | Milvus（现有 HNSW/COSINE 配置） | query 用现有 embedding 配置（text-embedding-v4, 2048 维）；`expr` 标量过滤：`company == "X" and period == "Y" and report_type == "Z"`（null 维度不拼入） |
| BM25 | 本地索引（`bm25s` 或 `rank_bm25` + jieba 分词） | 基于每份报告的 chunks JSON 构建分报告索引；filters 命中的报告集合内检索；查询词 = `rewritten_query` 分词 + 子查询 `keywords` 词项去重并入（BM25 查询扩展，P3 产出的 keywords 在此消费）；Milvus 2.4.15 无内置 BM25 全文检索（2.5+ 才支持 Function 级 BM25），故走本地实现，后续升级 Milvus 可迁移 |

### 6.2 融合、页级归并与重排序

```
每条子查询: 向量 top20 + BM25 top20 -> RRF 融合（rrf_k=60）
      │  全部子查询的融合候选合并
      ▼
页级归并: 候选 chunk 按（文件, 页码）去重（同页多分片合为一页）-> 回查整页原文
      │   -> 整页候选池（超过 rerank_candidates=20 时按页内最高 RRF 分预排序截取，
      │      不足则全取）
      ▼
重排序: Agicto qwen3-rerank 打分 -> 本轮取 top5 页（top_pages_per_loop=5，
        名额分桶：每条子查询先保底 1 页，剩余名额按全局 rerank 分补足）
      ▼
追加进证据池: 与历史轮次证据按（文件, 页码）去重合并
```

要点：

1. **证据粒度从 chunk 升级为整页**：检索命中的是 chunk 分片，同一页可能命中多个分片；
   按（文件, 页码）去重后回查整页原文，直接读 step3 产物 `data/03_flattened/{rid}.json`
   的 `pages[{page, text}]`（现成数据，零额外加工），整页送 rerank 打分；
2. **rerank 打分方式**：query 用该页命中子查询的 `rewritten_query`；一页命中多条子查询时
   取最高分，多意图场景各子查询公平竞争；打分文本用**整页原文**（不预截断），
   `max_page_tokens` 截断仅发生在注入 P4/P5 时；
3. **每个检索循环固定产出 5 页（名额按子查询分桶分配）**：先给每条子查询保底 1 页
   （该子查询候选中 rerank 最高分页，防多意图/对比场景某路证据被挤占），剩余 5-K 个
   名额按全部候选的 rerank 分全局排序补足；子查询数 K>5 时不再保底，直接全局取 5 页。
   一页命中多条子查询时归入其最高分对应的桶（与"取最高分"规则一致）。证据不足进入
   下一轮时，P4 的补充查询再产出新的 5 页，证据池跨轮累计（3 轮最多 15 页），
   与 §7 循环机制衔接；
4. 证据条目统一结构：`{page_key(文件+页码), text(整页原文), report_name, company,
   stock_code, report_type, period, page, rerank_score, source_sub_query_ids}`；
5. token 控制：单页超 `max_page_tokens`（默认 1500）截断注入；证据池全局受
   `evidence_token_budget`（默认 12000，整页粒度相应上调）约束，超限按 rerank 分数
   从低到高丢弃。

### 6.3 前置改造（进入本阶段前必须完成）

| 编号 | 改造项 | 原因 |
|---|---|---|
| R1 | Milvus schema 增加字段 `stock_code / report_type / period` 并重灌（step5 相应插入这三个字段） | 当前 schema 只有 company/report_name/page，无法做期间与类型过滤 |
| R2 | 新增 step6_build_bm25.py：读 `data/04_chunks/*.json` 构建 BM25 索引，输出 `data/05_bm25/{report_id}.pkl` | BM25 本地索引载体；重灌财报时同步重建 |

## 7. S5/S6 充分性判断与补充检索循环（LLM，提示词 P4）

### 7.1 循环机制

```
轮次 loop = 1..max_loops(3):
    S4 检索 -> S5 页级归并 + qwen3-rerank -> 本轮取 top5 页
    证据池按（文件, 页码）去重追加
    S6 调用 P4 判断:
        sufficient = true            -> 跳出，进入 S7
        sufficient = false 且 loop<3 -> 取 additional_queries 作为新一轮子查询，回到 S4
        sufficient = false 且 loop=3 -> 跳出，S7 降级处理
```

- 补充查询与首轮子查询结构一致（`query + filters`），走完全相同的混合检索通道。
- 证据池全局累计：每轮固定新增 5 页，第 2、3 轮的召回与之前轮次合并去重后一起参与判断
  与回答，避免"补充检索反而丢掉首轮证据"；受 `evidence_token_budget` 截断，优先保留
  rerank 高分页，但按子查询分桶保底——丢弃低分页时每条子查询至少保留其最高分 1 页
  （同 §6.2 要点 3 的名额分桶原则）。

### 7.2 判断口径（写入 P4）

- 数值型问题必须找到**具体数字 + 所属期间**才算充分；
- **指标口径一致性**：证据数值的指标定义与统计口径（指标含义、合并/母公司报表口径、
  单位）必须与问题一致；仅名称相近但口径不同的指标不得视为充分（如问"研发设备原值"
  不得用"固定资产净值"顶替，问"归母净利润"不得用"净利润"顶替）；
- 证据互相矛盾视为不充分，指出矛盾点；
- 补充查询必须带 filters，且同样遵守"禁止猜测"（只允许【原始问题】或【子查询计划】
  filters 中已确认的公司/期间/类型，否则 null——P4 看不到对话记忆，继承一律以
  子查询计划为准）；
- P4 与 P3 同源注入语料库范围枚举，补充查询 filters 不得出现库外枚举值；
  库外期间/报告类型（如库内仅 2024 年报而用户问 2023）写入查询句文本，不进 filters
  （走查实证：period="2023" 进 filters 会导致两路检索 0 命中、白烧 2 轮循环）。

## 8. S7 回答生成（LLM，提示词 P5）

- 输入：原始问题 + 查询计划（sub_queries）+ 最终证据池。
- 输出 JSON：`{insufficient, missing_info[], answer}`。
- 规则：
  1. 仅依据证据作答，每条结论标注来源（报告文件名 + 页码）：
     `[来源: 中芯国际2024年年度报告 P23]`；
  2. 多子问题分点回答，逐点对应；对比型逐项对比后给结论；
  3. **允许基于证据数值做四则运算**（占比、增速、差额等），但必须列出计算式、标注参与
     计算数值的来源页，并把计算结果标明为"计算值"（报告原文未直接给出）；
     参与计算的数值在证据中找不到时禁止计算；
  4. 证据无依据的子问题**明确标注"未在现有资料中找到"**并写入 `missing_info`，严禁编造；
  5. 全部子问题无依据 → `insufficient=true`，服务端用**信息不足固定话术**直接告知用户
     （同样不走 LLM 自由发挥），并附上"可尝试的改问方式"建议（基于 missing_info 生成）。
- **来源标注程序级校验（防谎报页码）**：S7 返回后，程序解析 `answer` 中的全部
  `[来源: 报告名 P页码]` 标注，与证据池 page_key（report_name + page）集合求交集：
  越界标注（证据池中不存在的页）直接从 answer 文本中剔除该条标注，并在 sources[]
  对应条目标记 `verified=false`、记 warning 日志——假来源比无来源危害更大，宁可少标
  不可错标；校验不阻塞回答返回。
- 话术模板（可配置，默认）：
  > 很抱歉，我在已入库的财报资料中未能找到足以回答该问题的内容。您可以尝试：明确公司
  > 名称与报告年份（如"中芯国际 2024 年报的营业收入"），或将大问题拆成小问题分别提问。

## 9. LLM 提示词总表（完整文本，落盘为 `config/prompts/qa/*.md`）

> 通用约定：所有提示词中 `{变量}` 为运行时注入占位；模型输出必须是**纯 JSON**（不带
> markdown 围栏）；temperature=0。
>
> **JSON 输出两级防线**（所有 LLM 步骤通用）：
> 1. 首选 API 级结构化输出：若网关/模型支持 `response_format` JSON mode，调用时启用
>    （格式由接口层强制；可用性在实现阶段实测确认，不支持则退化为纯提示词约束）；
> 2. 格式修复旁路：JSON 解析失败时不立即原样重试，先调用 P6（格式修复模块）把坏输出
>    重新格式化为合法 JSON（只修格式、不改内容）；修复后仍解析失败再走原重试流程
>    （`llm.max_retries`），最终失败才返回"服务暂时不可用"。

### P1 意图识别（`config/prompts/qa/P1_intent.md`）

```text
你是财报问答系统的意图识别模块。请判断用户的最新输入是否属于"上市公司财报相关提问"。

属于财报相关的例子：
- 财务数据：营业收入、净利润、总资产、负债、现金流、毛利率、研发投入等
- 经营内容：主营业务、产品线、产能、客户与供应商、经营分析讨论
- 报告结构：某份报告某章节说了什么、审计意见、股东结构、分红方案
- 对比与追问：不同报告期数据对比；结合对话历史的财报话题追问

不属于财报相关的例子：闲聊寒暄、写代码、旅游/娱乐/生活咨询、与财报数据无关的
新闻或通用知识问答。

判断依据：
1. 问题的答案是否可能出现在上市公司财报文本中；
2. 结合对话历史：若本条是追问/省略表达，且对话主题是财报，则视为相关；
3. 只提公司名或只说"帮我查个东西"而无实质内容时，视为相关（交由后续流程澄清）。

输出 JSON：
{
  "is_financial_qa": true 或 false,
  "reason": "一句话判断依据",
  "confidence": 0 到 1 之间的小数
}
```

### P2 记忆压缩（`config/prompts/qa/P2_memory_compress.md`）

```text
你是对话记忆压缩模块。请将【已有摘要】与【待压缩对话】合并压缩为一份新的结构化摘要，
供后续财报问答的上下文使用。

必须保留（优先级从高到低）：
1. 出现过的公司名称、股票代码（及用户切换公司的轨迹）；
2. 提到过的报告期、报告类型；
3. 已回答过的主题及关键结论要点（含具体数字时保留数字与期间）；
4. 用户表达的约束或偏好（如"只看年报""和港股对比"）。
```

### P3 查询改写（`config/prompts/qa/P3_rewrite.md`）

```text
你是财报问答系统的查询改写模块。请结合【对话记忆】把用户的【最新问题】改写为适合
检索的结构化查询计划。

改写规则：
1. 指代消解：把"它、这个、都、还有、其他"等指代词与省略成分补全为明确对象；
   优先继承对话记忆中最近确认的公司、报告期、报告类型。
2. 多意图拆分：问题中包含多个可独立回答的子问题时，必须拆成多条子查询；
   对比型问题按对比对象各生成一条子查询（对比结论由后续回答环节综合）。
3. 反问还原：反问句或带情绪的表述，先还原为中立、客观的信息需求再拆分。
4. 缩小检索范围线索（filters）四项：
   - company：公司名称；确定公司时可同时给 stock_code；
   - period：报告期，格式如 "2024" ；
   - report_type：只能是 年报 / 半年报 / 一季报 / 三季报 之一；
   filters 只允许取自【最新问题】或【对话记忆】中明确出现过的信息，
   并尽量与【语料库范围】中的枚举对齐；无法确认的字段一律填 null，严禁猜测或编造。
5. rewritten_query 必须是自包含的完整检索语句：即使 filters 已含公司名，
   查询句中也要写全"公司 + 期间 + 主题"。

语料库范围（仅供对齐枚举，不得超出）：
- 公司：{company_list}
- 报告期：{period_list}
- 报告类型：年报、半年报、一季报、三季报

query_type 取单词值：single=单意图，multi=多意图，compare=对比，rhetorical=反问还原。

输出 JSON（单意图时 sub_queries 也只输出一个元素）：
{
  "query_type": "single | multi | compare | rhetorical",
  "sub_queries": [
    {
      "id": 1,
      "rewritten_query": "自包含的完整检索语句",
      "search_intent": "这条子查询要查什么（一句话）",
      "filters": {
        "company": null,
        "stock_code": null,
        "period": null,
        "report_type": null
      },
      "keywords": ["关键词1", "关键词2"],
      "confidence": 0 到 1 之间的小数
    }
  ]
}
```

> `keywords` 语义：该子查询的核心词项（指标名/主体名，2~5 个，不含 filters 已含的
> 公司/期间/类型），供 S4 BM25 查询扩展；无合适关键词时给空数组。

### P4 充分性判断（`config/prompts/qa/P4_sufficiency.md`）

```text
你是财报问答系统的证据充分性评审模块。请判断【已召回证据】是否足以回答用户的问题。

判断标准：
1. 充分 = 每个子问题都能从证据中直接找到答案所需的数据或原文表述；
   数值型问题必须能找到具体数字及其所属期间（仅有结论无数据不算充分）；
   证据数值的指标口径必须与问题一致——仅名称相近但口径不同（如"固定资产净值"对
   "研发设备原值"、"净利润"对"归母净利润"）不算找到，视为不充分。
2. 证据之间相互矛盾时视为不充分，并在 missing_points 中指出矛盾点。
3. 不充分时给出 1 到 3 条补充检索查询（additional_queries）；
   每条的 filters 只允许使用【原始问题】或【子查询计划】的 filters 中已确认的
   公司/报告期/报告类型（本模块看不到对话记忆，不要凭空继承），无法确认则填 null，
   严禁猜测。
4. filters 取值不得超出语料库范围。库内没有的期间或报告类型（如库内只有 2024 年报，
   用户却问 2023 年数据）一律不写进 filters，改写为查询句文本参与检索。

已召回证据：
{evidence}

原始问题：{question}
子查询计划：{sub_queries}
当前是第 {loop} 轮检索（最多 3 轮）

语料库范围（filters 取值仅供对齐枚举，不得超出）：
- 公司：{company_list}
- 报告期：{period_list}
- 报告类型：年报、半年报、一季报、三季报

输出 JSON：
{
  "sufficient": true 或 false,
  "missing_points": ["缺少的信息点", ...],
  "additional_queries": [
    {"query": "补充检索语句", "filters": {"company": null, "stock_code": null, "period": null, "report_type": null}}
  ],
  "reason": "一句话结论依据"
}
sufficient 为 true 时，additional_queries 与 missing_points 均给空数组。
```

## 12. 边界与异常处理

| 场景 | 处理 |
|---|---|
| 任一 LLM 步骤 JSON 解析失败 | 两级防线：①先走格式修复旁路（P6，只修格式不改内容）；②修复后仍失败再重试（复用 `llm.max_retries`），最终失败返回"服务暂时不可用"并记日志，不静默兜底 |
| 意图识别置信度低（<0.5） | 按财报相关放行（宁可多检索，不误拒） |
| 某子查询召回为空 | 该子查询证据记空，进入 S6 判断；连续两轮为空在 missing_points 中明确列出 |
| rerank 调用失败 | 重试（复用 `llm.max_retries`），仍失败返回"服务暂时不可用"并记日志；不静默跳过重排序（宁可不答，不给未精排结果） |
| 单页文本超长 | rerank 打分用整页原文（不预截断）；注入 P4/P5 时按 `max_page_tokens` 截断 |
| filters 全为 null | 允许（用户未提任何范围线索），全库检索，但 P3 已要求查询句自包含兜住召回质量 |
| 同会话高频提问 | 每会话加锁串行处理，避免记忆压缩与问答交错 |
| 语料库为空/服务不可用 | 启动时自检（Milvus 连接 + BM25 索引存在性），不通过拒绝启动 |
| 用户更换话题/公司 | 由 P3 按对话记忆重新解析 filters，旧公司线索只在被再次确认时继承 |

## 13. 验收清单

| 项 | 验收标准 |
|---|---|
| Web 与会话 | 提问、回答、来源列表正常展示；关闭页面后重开会话，记忆为空（不记得之前聊的公司） |
| 记忆压缩 | 连续多轮对话超过 3000 token 触发压缩；摘要保留公司/期间/类型实体；最近 4 轮原文完整 |
| 意图识别 | 财报相关问题全部放行；闲聊/无关问题收到委婉拒绝且不触发检索，该轮已写入会话记忆 |
| 查询改写 | 多意图拆分为多条子查询；每条子查询 filters 完整或合理为 null；无编造的公司/年份 |
| 混合检索 | 每条子查询独立返回向量 + BM25 两路结果并完成 RRF 融合；filters 正确下发（对照 Milvus expr 与 BM25 报告集合） |
| 页级归并与重排序 | 候选按文件+页码去重、整页内容取自 03_flattened；每轮经 qwen3-rerank 精排后恰好产出 5 页且名额分桶正确（多子查询场景每条子查询至少 1 页）；rerank 分数与耗时入日志 |
| 循环检索 | 证据不足时能看到第 2/3 轮补充查询与合并去重后的证据池；总轮次不超过 3 |
